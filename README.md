## Мой вклад

 Моя основная зона ответственности — backend и инфраструктура вокруг него.

Я реализовал:

- PostgreSQL repository layer для основных сущностей и агрегированной активности;
- bootstrap, entry point и composition root backend-сервиса, конфигурацию, Docker-окружение и воспроизводимый seed generator;
- персональные рекомендации и безопасный публичный recap;
- backend-controlled CTA и redirects;
- unit-, integration- и E2E-тестирование;
- CI для lint/test/integration/E2E;
- production deployment pipeline с Docker/GHCR, smoke checks и rollback.
  
Помимо backend-задач, я доработал пользовательский сценарий на frontend: экраны выбора профиля и просмотра recap, рекомендации, quiz перед любимой категорией, публичный просмотр итогов по ссылке и интегрировал эти сценарии с API.

  ## Repository layer

Я реализовал PostgreSQL-репозитории для:

  - профилей пользователей;
  - агрегированной пользовательской активности;
  - recap;
  - объявлений для рекомендаций;
  - публичных snapshot-версий recap.

  
Persistence отделён от бизнес-логики интерфейсами на стороне use case. Благодаря этому бизнес-логика не зависит от PostgreSQL и тестируется с mock-реализациями repository.
  
Там, где database representation отличается от domain model, используются отдельные database models и converters — например, для nullable-полей, JSONB-слайдов и причин архетипа.

Работа с PostgreSQL выполняется с отдельным configurable operation timeout. Backend не позволяет зависшему database query бесконечно удерживать HTTP request и ресурсы connection pool.

### Агрегация пользовательской активности

Годовая активность собирается из нескольких источников - `views`, `favorites`, `deals`, `messages` и `listings` - в единую event-модель внутри SQL CTE.

PostgreSQL сразу вычисляет active days, просмотры, избранное, покупки, продажи, сообщения, затронутые категории и другие агрегаты, а backend получает компактную domain model вместо полного набора событий.

Так аналитическая агрегация выполняется рядом с данными и не требует загружать годовую историю пользователя в application memory.

Временные выборки используют UTC и half-open интервалы `[from, to)`, поэтому соседние периоды не пересекаются и не требуют искусственного «последнего момента дня или года».

  ### Целостность и идемпотентность recap

Генерация recap имеет два уровня идемпотентности.

Use case сначала проверяет наличие результата по `(profile_id, year)`, чтобы не выполнять повторно вычисление метрик и сборку слайдов.

При этом корректность не зависит от предварительного lookup: на уровне PostgreSQL существует unique constraint, а создание выполняется через `INSERT ... ON CONFLICT DO NOTHING`. 
Поэтому даже два конкурентных запроса не могут создать два recap для одного пользователя и года. Предварительный lookup работает как оптимизация, а constraint базы данных остаётся источником истины.

  ## Генератор демонстрационных данных

Для воспроизводимой демонстрации я реализовал отдельный транзакционный seed-генератор пользовательской активности, которвый создаёт связанные профили, категории, объявления, просмотры, избранное, сообщения, покупки и продажи.

Детерминированность seed реализована не только фиксированным random seed. Стабильные UUID выводятся из namespace и смыслового ключа через hash-based generation, а для разных сценариев создаются независимые производные random streams.

Благодаря этому demo dataset воспроизводим: одинаковые (year, seed) дают стабильные идентификаторы и события, что удобно для тестов, frontend-интеграции и повторного развёртывания demo.

Seed различает корректно загруженный dataset и partial state. Это позволяет не маскировать повреждённое demo-окружение повторным запуском генератора. Вся запись выполняется в одной PostgreSQL-транзакции, поэтому новый partial state не возникает при ошибке посередине загрузки. Для массовой загрузки событий используется pgx.CopyFrom.

  ## Персональные рекомендации

  Я расширил сценарий формирования recap персональными объявлениями.

  Система:

  - находит самое старое избранное объявление пользователя, которое всё ещё активно;
  - определяет любимую категорию по активности за год;
  - выбирает до трёх актуальных рекомендаций;
  - сначала отдаёт объявления из любимой подкатегории;
  - исключает собственные объявления пользователя, уже добавленные в избранное и завершённые сделки.

  Полученные данные добавляются в слайды избранного и любимой категории. Рекомендации являются optional enrichment основного recap: если подходящих объявлений нет, основной сценарий продолжает работать, а дополнительный блок просто не добавляется.

Таким образом отсутствие рекомендаций не влияет на основной сценарий генерации recap.

 ### Backend-controlled navigation

Для CTA и переходов по рекомендациям frontend не передаёт destination URL.

Клиент передаёт только разрешённое действие или ID рекомендации, после чего backend проверяет данные относительно сохранённого recap и самостоятельно формирует URL назначения.

Это исключает произвольный redirect URL со стороны клиента. Для поисковых URL параметры формируются через `net/url`, а целевой домен задаётся backend'ом.

  ## Публичный recap

  Я реализовал возможность поделиться безопасной версией итогов по постоянной ссылке, разделив личный recap и публичное представление на уровне backend. Публичная ссылка указывает не на исходный recap, а на отдельный immutable snapshot с allowlist полей.
  
  - расширил OpenAPI-контракт endpointами создания и получения публичного recap;
  - реализовал отдельный usecase;
  - добавил HTTP-конвертеры и обработчики;
  - создал PostgreSQL-репозиторий и миграцию `shared_recaps`;
  - реализовал генерацию криптографически случайного публичного токена;
  - сделал создание публичной ссылки идемпотентным.

  Публичная версия формируется на стороне backend по разрешённому набору полей. В неё не попадают фамилия, идентификаторы профиля и исходного recap, причины архетипа, сообщения, покупки, продажи, суммы и конкретные объявления.

  Snapshot сохраняется при первом sharing и больше не пересчитывается, поэтому содержимое уже опубликованной ссылки не меняется вместе с внутренней моделью recap.


  ## Тестирование

### Unit tests

Покрыты бизнес-правила recap, рекомендации, navigation, sharing, token generation, преобразование данных и error scenarios.

### Integration tests

Repository layer проверяется на настоящем PostgreSQL через Testcontainers.

Тесты поднимают PostgreSQL, применяют реальные migrations и проверяют: SQL-запросы, ограничения схемы, JSONB и преобразование database model ↔ domain entity.

### E2E

Добавил backend HTTP journey, который запускает реальные repository и usecase реализации поверх PostgreSQL и проходит основной сценарий через HTTP API:

`profile → create recap → get recap → share → public recap`.

Дополнительно E2E проверяет идемпотентность повторной генерации и sharing, а также то, что публичный recap не раскрывает приватные поля.

В командном CI unit- и integration-тесты запускаются с race detector, а backend E2E является отдельным stage перед production release.
